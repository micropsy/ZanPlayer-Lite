# Project agent notes

## Commands
- Frontend: `npm run dev`, `npm run build` (`tsc && vite build`), `npm run test` (vitest)
- Rust: `cargo test` then `cargo build --features vlc-native` (must keep linking to the real `/Applications/VLC.app` libvlc.dylib)
- Native engine: `npm run tauri dev -- --features vlc-native` (macOS embeds LibVLC via `set_nsobject` into a dedicated host NSView below the transparent webview — there is no Render API/Metal path anymore; the old `native-player`/`macos-render` features are gone). Plain `cargo build`/`npm run tauri dev` (feature-off) ships the HTML5 `<video>` fallback. **macOS RELEASE builds are vlc-native with LibVLC BUNDLED into the .app**: run `bash scripts/bundle-vlc.sh` (stages `libvlc{dylib,ccore}` + `plugins/` from `/Applications/VLC.app` into `src-tauri/vendor/vlc`, gitignored) then `tauri build --bundles app,dmg --features vlc-native`; `tauri.macos.conf.json` copies `vendor/vlc` into `Contents/Resources/vendor/vlc/`, and `build.rs` emits the bundle-first rpath `@executable_path/../Resources/vendor/vlc/lib` (system VLC rpath second, so unbundled dev builds still resolve). The runtime plugin path prefers the bundled tree. Proven self-contained by the 10/10 smoke run loading libvlc from `Resources/vendor/vlc/lib` while playing an MKV. Linux/Windows releases stay feature-off (HTML5 fallback).
- Release: `npm run release -- <major|minor|patch>` (the only path that builds a GitHub release; plain `git push` runs only tests)
- Smoke test: `ZANPLAYER_NATIVE_SMOKE=1 ZANPLAYER_NATIVE_SMOKE_VIDEO=/path/to.mp4 npm run tauri dev -- --features vlc-native` — auto-loads a file through the real VLC session and prints `[native-smoke]` logs to stderr, ending `RESULT: N/10 passed` on macOS (N/5 elsewhere; mobile returns early). Checks, in code order (`native_player/mod.rs` `smoke_load`): (1) libvlc session initialized, (2) `load` accepted the path (`vlc-loaded` emitted), (3) [macOS] the dedicated host NSView is attached to the window hierarchy, (4) [macOS] the session reports the embed target intact (`embed_ok`), (5) media left Opening/NothingSpecial within 5 s (`wait_loaded` — demuxed, not in error), (6) playback clock advances within a 12 s window (decode proven), (7) a playing state was reached at least once, (8) [macOS] host view anchored to the measured DOM player area, (9) [macOS] applied rect is non-degenerate (>100×100), (10) [macOS] DOM over the player-area centre is transparent (alpha < 0.5). There is NO frontend-engine assertion — the harness never checks `engine === "VLC"`. Because the harness webview sits in the app's empty state, it injects an rAF + `resize` loop that measures the largest full-window DOM region (NOT `[data-player-viewport]`) and dispatches it through the SAME `apply_surface_layout` the product reporter feeds `vlc_set_layout` with; a smoke-only stylesheet (`.zanplayer-smoke-clear`) strips background/foreground paint inside the measured area while the sidebar keeps its opaque paint. The "applied" rect read back via `macos_surface::applied_js_rect` (inverse of `apply_layout`, converted back to JS coords) is the ACTUAL rendered host frame — never just the rect the webview requested — so a misconverted or drift-accumulated host view fails checks 9/10 instead of hiding behind the requested rect. `ZANPLAYER_NATIVE_SMOKE_PAUSE=1` pauses 30 s after the checks instead of auto-exiting (compile-time `PAUSE_SECS`, only compiled under `vlc-native`).

## Native player engine
- In-window LibVLC backend behind the **`vlc-native` cargo feature**; macOS production builds ship it BUNDLED (see Commands), while Linux/Windows releases and un-featured local builds are HTML5 (`<video>`).
- **Hand-rolled C FFI against the system VLC.app install** — no crate, no `#[link]` attribute. build.rs emits the `rustc-link-search`/`rustc-link-lib` rfags and the `.app` deps are collected via `otool -L` → `rcodesign` (sandbox resource dir + fence for the ffi dylibs; stub/no-op on Linux). Path: `libvlc` dylib at `/Applications/VLC.app/Contents/MacOS/lib` (compat 12.0.0 / current 12.1.0, reports client API 3.0 via the `libvlc.h` macros in `libvlc.rs`). `VlcPlayer` holds raw `*mut libvlc_instance_t` / `*mut libvlc_media_player_t` with `unsafe impl Send + Sync` and a Drop guard — the E0277 "cannot be sent between threads safely" error on these raw pointers is EXPECTED and handled by those impls (the underlying objects are thread-safe VLC state).
- **Plugin discovery is the #1 `libvlc_new` failure**: VLC.app keeps plugins at `Contents/MacOS/plugins` but the dylibs at `Contents/MacOS/lib`, so a bare `libvlc_new()` fails ("failed to create libvlc instance"). The `--plugin-path` CLI arg was REMOVED in VLC 12 ("Warning: option --plugin-path no longer exists.") — the fix is `VlcPlayer::new()` calling `std::env::set_var("VLC_PLUGIN_PATH", …)` BEFORE `libvlc_new`. `vlc_plugin_dir()`: on macOS+Windows reads `VLC_PLUGIN_DIR` env → else `VLC_PREFIX` env → else default `/Applications/VLC.app/Contents/MacOS/lib` (falling back to `VLC_LIB_DIR`), plugin = lib_dir.join("../plugins") if it exists; non-macOS unix uses `VLC_PLUGIN_DIR` only. Regression-covered by `libvlc::tests::new_instance_and_drop_are_stable`.
- **libvlc semantics that bite**: `libvlc_media_player_pause` TOGGLES — `VlcPlayer::pause()` calls it only when `is_playing()`, `resume()` only when paused. `play()` is idempotent. SPU rendering is disabled (`libvlc_video_set_spu(player, -1)`) — captions/OSD live in the webview. `libvlc_video_set_key_input/set_mouse_input(0)` on macOS so the host view never steals clicks. Windows uses child-HWND attach (`set_hwnd`); Linux X11 uses `set_xwindow` (no Wayland backend).
- **Embed target is a DEDICATED host NSView, never the WKWebView/window view.** The classic "VLC opens a separate floating window" bug is WebKit pruning foreign subviews of the webview it owns. `session.rs` → `embed_surface` returns `macos_surface::host_view(app)`: a plain layer-backed (`setWantsLayer`), retina-aware (`contentsScale = backingScaleFactor`) NSView inserted as a sibling BELOW the transparent webview (`addSubview:positioned:NS_WINDOW_BELOW`), cached in the leaked `static HOST_VIEW: Mutex<Option<ViewPtr>>` at `macos_surface` MODULE scope (declaring it inside `host_view()` breaks `host_still_attached()` in session.rs with E0425). objc2 0.6 gotchas it encodes: raw `*mut AnyObject` statics need a `Send + Sync` wrapper (`ViewPtr`) for `MsgSend`-able access, and by-value marshalled `NSPoint/NSSize/NSRect` need `unsafe impl Encode` (`Encoding::Struct("CGPoint"/"CGSize"/"CGRect", …)`).
- **Stage anchoring = `vlc_set_layout`**: `VideoPlayer.tsx` runs a layout reporter while `engine === "VLC"` that reads the canonical `[data-player-viewport]` column's `getBoundingClientRect()` (CSS px, top-left origin) — the App shell's content column that is a flex sibling of the sidebar — and invokes `vlc_set_layout` with a `SurfaceLayout { x, y, width, height }`. It is event-driven: a viewport `ResizeObserver` plus explicit `window` `resize` + `document` `fullscreenchange` listeners (plus a `zan-fullscreen` event listener — Tauri window fullscreen never fires the DOM `fullscreenchange`) coalesce into at most one rAF per frame; a `vlc-loaded` event re-asserts the anchor after a fresh host. Sidebar toggles cause App shell flex reflow, which fires the viewport's RO — the Player never subscribes to sidebar state. **The Player consumes the PlayerViewport rect VERBATIM** (regression-covered by `VideoPlayer.test.tsx` "re-anchors exactly when sidebar expand/collapse reflows the PlayerViewport") — it never re-derives the rect against sidebar geometry: App shell flex already placed the column, so the measured box IS the region. The one exception is a **right-of-sidebar INVARIANT** (`enforceRightOfSidebar` in `videoLayout.ts`, wired into the reporter): while the OPAQUE inline sidebar is on the page (`[data-sidebar]` with `position !== "absolute"`), the rect sent to `vlc_set_layout` is forced to start at the sidebar's right edge — a stale or mid-toggle viewport rect can never make the picture paint under/over the sidebar (an identity in every correct flex state; tests `VideoPlayer.test.tsx` `[B2]` + `videoLayout.test.ts`). Drawer mode (`position: absolute`, mobile) is NOT enforced — there the opaque drawer overlays the video by design. **Graceful missing element**: if `[data-player-viewport]` is absent the reporter sends no native layout and retries per frame until it mounts. `overflow-clip` on the `data-player-viewport` column and the player root/stage physically prevents the HTML5 fallback box and DOM overlays from painting outside the viewport — subtitles, controls, OSD are clipped; the sidebar never clips. Values are coalesced to whole CSS px so IPC never spams. Degenerate (0×0) rects are skipped on the Rust and JS sides so the surface can never collapse to a top-left patch while the layout settles. **Native dispatch** (`apply_surface_layout`): **macOS** `macos_surface::apply_layout` computes the host frame DIRECTLY in content coords — never `convertRect:fromView:` (its result depends on the destination view's current frame, so one wrong frame made every later frame drift off the stage). Since the host NSView and WKWebView are unflipped siblings under the content view: `content.x = webview.frame.x + x`, `content.y = webview.frame.y + webview.bounds.height − (y + h)` (flip), clamped into the webview bounds; then `setFrame:` + `setNeedsDisplay:` + `setNeedsLayout:`; the video re-applies on the next `vlc_set_layout`. **Windows** `resize_vlc_window` scales px by `GetDpiForWindow/96` and `SetWindowPos(HWND_TOP, SWP_NOZORDER|SWP_NOACTIVATE)` on the VLC-child HWND; **X11** `resize_vlc_window` targets the top-most non-webview (cached) child and `configure_window` x/y/Some(width)/Some(height), DPI-scaled. Every rect passes through `sanitize_surface_layout` (finite, non-negative).
- **Embed probe**: `session.rs` `load()` emits `vlc-embed-ok` carrying `embed_ok()` (load-time); on macOS `embed_ok()` reflects `macos_surface::host_still_attached()` and it is always `true` on the Windows/X11 embed sessions. The macOS desktop ticker then RE-PROBES the host on every 250 ms beat: `macos_surface::probe_attachment` re-runs the real AppKit hierarchy check (host superview/window/non-degenerate frame) on the main loop via `run_on_main_thread` and refreshes an `ATTACHED` atomic cache; when the cache flips to detached, the ticker emits `vlc-embed-lost` exactly once per `load` (`should_emit_embed_lost`, re-armed by each load — this closed the old Todo.md "per-beat host probe" gap). Windows/X11 tickers do not emit `vlc-embed-lost` (their per-beat child pin already re-anchors the video); the `vlc-embed-lost` event is also emitted by the mobile backend (`mobile.rs`, once when the position poll keeps failing). Desktop's running-window safety net is this per-beat probe PLUS the 5 s decode watchdog (next bullet) plus the load-time `vlc-embed-ok` result. `VideoPlayer.tsx` listens for `vlc-embed-lost` and cuts straight to HTML5 on it.
- **Fullscreen is Tauri WINDOW fullscreen, never the HTML Fullscreen API.** `document.documentElement.requestFullscreen()` reparents the WKWebView into a SEPARATE macOS fullscreen window, leaving the dedicated host NSView stranded in the old window — the player area renders permanently black. The product's fullscreen button (`VideoPlayer.tsx` `toggleFullscreen` → `TauriService.setWindowFullscreen`) instead runs `set_window_fullscreen` (`native_player/mod.rs`), which calls `set_fullscreen` on the SAME window: webview and host NSView grow together into the fullscreen Space, and the layout reporter just re-anchors on the resize. The backend emits `zan-fullscreen` right after `set_fullscreen` (before the Space animation settles), and every consumer that previously listened to the DOM `fullscreenchange` ALSO listens to `zan-fullscreen` — App.tsx (hide top strip + sidebar), `VideoPlayer` (mirror `isFullscreen` for the icon/`"F"` key), and the layout reporter (synchronous re-anchor, since window fullscreen never fires the DOM event).
- **Native decode watchdog** (undecodable/corrupt files): `libvlc_media_player_play` returns OK for a file VLC ultimately cannot demux/decode (renamed path, corrupt container, headless codec), so no load error surfaces and the player would strand on a silent black frame. `VideoPlayer.tsx` runs a 5 s (`NATIVE_DECODE_WATCHDOG_MS`) grace timer whenever the engine is `VLC`: if the 250 ms clock never reports a real duration or advancing playhead (`nativeDecodeProvenRef`, set by the clock-mirror listener), it cuts back to the HTML5 blob engine exactly like an embed loss — the fallback's own `onError`/container hint then explains the failure. It must NOT register a competing `vlc-timeupdate` listener (the test harness stores one listener per event name, which would clobber the clock mirror) — it reads the shared decode-proof ref instead.
- macOS transparency requires BOTH `app.macOSPrivateApi: true` (tauri.conf.json) AND the `macos-private-api` tauri feature (Cargo.toml). Without them the webview stays opaque and the VLC surface is invisible.
- **App-window frame integrity / no background bleed**: the window is `transparent: true` so the host view (behind the webview) shows through — chrome must paint its own opaque DOM backgrounds. `tauri.conf.json` uses `"titleBarStyle": "Overlay"` + `"hiddenTitle": true` (Tauri 2.11.2 schema `WindowConfig`) so the native macOS title bar is gone and the traffic lights float over the DOM; `App.tsx` renders a solid `h-10` top strip (theme `bg-zan-black`/`bg-white` + border-b, NO `data-tauri-drag-region` attribute — see the drag paragraph below) holding the `Open sidebar` hamburger, and the content row (`relative flex min-h-0 flex-1 overflow-hidden`) wraps `Sidebar` + the main column. On macOS the strip clears the traffic-light group with `pl-[76px]` (gated by the `isMacOs()` UA check in `tauri.ts`; non-Mac keeps `pl-2`), so the `Open sidebar` toggle never crowds the native close/minimize/zoom buttons; the `flex-1` drag region fills the rest with `pr-2`. Desktop can no longer show through the title bar because the strip itself is opaque; the main area is covered by the `VideoPlayer` root (`bg-black` in every non-native state). The top strip is hidden in web fullscreen via `isFullscreenUi` (a `fullscreenchange` listener mirrors `document.fullscreenElement`). The strip and its `flex-1` spacer are the ONLY drag surface: a real mousedown drives `TauriService.startWindowDrag()` → the backend `start_window_drag` command (`src-tauri/src/native_player/macos_window.rs`, compiled into EVERY build, feature-off included). WKWebView does NOT honor `-webkit-app-region: drag` (Chromium-only), and Tauri's `data-tauri-drag-region`/core `startDragging` read `NSApp.currentEvent`, which a FOCUSED webview has already consumed by IPC time — so dragging silently died exactly when the app was active. `start_window_drag` instead synthesizes a fresh `LeftMouseDown` (`NSEvent mouseEventWithType:`) at the live cursor and calls `performWindowDragWithEvent:` on the AppKit main thread (tao's own synthesis pattern), so the window drags focused or not; non-macOS keeps the core `startDragging` path. The mousedown handler excludes interactive children (buttons/inputs/links) so clicks keep working while chrome space drags the window.
- **Layering**: on macOS the host NSView is structurally BELOW the transparent webview (the `addSubview:positioned:NS_WINDOW_BELOW` from embed_surface) so DOM captions/controls/OSD always paint above the picture without per-tick re-sorts; `keep_webview_on_top` still re-runs on each ticker beat and after every `load`, posting the z-order re-stack (`addSubview:positioned:` on host + webview — deliberately NOT `setFrame:`) to the AppKit main loop via `AppHandle::run_on_main_thread` (`let _ = app.run_on_main_thread(...)` — the `if` wrapper was a lark, the closure returns `Result`, hence `let _`). A background `setFrame:`/`addSubview:` would race `apply_layout`/`apply_surface_layout`, which read the same `webview_frame` on the main thread; keep any new view mutation there (post it to the main loop), never in a ticker/spawned thread; and never reassert the webview frame in the repin — `apply_layout` + the JS right-of-sidebar clamps already own the positioning. **Windows** `windows_layering` finds the child HWND whose parent is ours (the VLC video subclass) and `SetWindowPos`s the webview HWND to HWND_TOP; **X11** `x11_layering` caches the webview XID from the pre-VLC child set and re-raises it above the video child. **Wayland has no client-side z-order** — stacking is compositor-owned, so frosted captions may sit under the video there (no back-end by design).
- The Windows (`windows_layering`/`resize_vlc_video_window`) and X11 (`x11_layering`/`resize_vlc_window`) FFI arms are `cfg`-gated and do NOT compile on the macOS host. They are type-checked against real `windows-sys` / `x11rb` versions via throwaway scratch crates in the system temp dir (the full cross `cargo check` is blocked by the `ring` C toolchain). If you touch those arms, re-verify that way — `cargo test`/`clippy` on macOS will not see them.
- **PTS sync**: `vlc-timeupdate` is a ~250 ms ticker that is **coalesced** — `session.rs` emits only when `snapshot_changed` (position moved ≥ `POSITION_EPSILON` (0.05 s) vs the last beat, or paused/ended/duration changed). The React clock, progress bar, and subtitle render queue read strictly from this single payload (`vlcClock`, `libvlc_time`/1000 to seconds), never from HTML5 `timeupdate`/rAF, so there is one source of truth for time.
- **Unified native seek funnel**: `VideoPlayer.tsx` `seekNative` (via `seekNativeRef`) is the ONLY native-mode seek path — drag bar, skip fwd/back, seek-to editor clicks, and auto-resume all route through it. Contract: `clearPendingSeek()` → clamp target to known duration → optimistic `setCurrentTime` (drives editor/recents; the playback clock stays on the backend tick) → `notifyPipelineSeekRef.current(target)` → `vlcSeek` (VLC `timeSet`, absolute ms). Backend: `seek_transcription` purges the `RenderQueue` (stale pre-seek cues) BEFORE forwarding through `SeekControl`/`seek_rx`, so live passes drop their VAD buffers and reposition the WAV reader to the same PTS.
- **Job identity / render-queue scoping**: every `start_transcription(..., jobId)` run is scoped by `job_id` back-to-front. The queue stores `QueuedCue { job_id, cue }` and is drained per-job (`poll_transcript_cues(job_id)` → `drain_job`), purged per-job on seek (`clear_job`), and all `transcription-progress`/`done`/`error`/`batch-done` events carry `job_id`. A new managed `ActiveJob { job_id }` slot is set at start, compare-and-cleared at job end, and read by `transcription_active(job_id)` — the frontend polls it every 150 ms as a completion safety net so a *missed* final event (fast batch run, listener torn down mid-job) never strands the `isTranscribing` flag and silently blocks the next auto-transcription. Frontend guards drop any event whose `job_id` doesn't match `transcriptionJobIdRef.current` (a previous file's still-decoding job can't surface cues or finalize state). Language change regenerates the generated track exactly once per spoken ISO code (`lastGenLanguageRef`), so stale generated tracks from the old language never linger. A failed run surfaces a **Retry** action in the CC menu that clears the error, drops partial generated tracks (`removeGeneratedTracks`), and starts a fresh job for the same file (`retryTranscription`) — no video reload, and the fresh `job_id` isolates it from the dead worker.
- **HTML5 fallback container limits**: WebKit/Safari can't demux MKV/AVI/FLV/WMV and Chromium plays a narrow MKV codec subset, while native VLC/ffmpeg handles every catalogued container. `mediaFormats.ts` ships `isHtml5Playable(fileName)` / `html5UnsupportedHint(fileName)`; the `<video onError>` overlay (`videoLoadError`, `z-[25]`) shows a visible "this container isn't supported by the fallback player" message instead of a silent black frame — subtitles can still appear since ffmpeg decodes the audio natively. **Every media entry point classifies by file extension only** (`isMediaFile(file.name)`, lowercased): App root drag-drop, Sidebar browser `<input>`, Sidebar drag-drop, and the native `open_video_dialog` filter — browser/OS MIME types are never consulted, so an MKV drop labeled `audio/*` (or empty) can't be misrouted as audio.
- **Z-order layer scale** (native): root stays transparent; DOM overlay stack must keep explicit Tailwind z-indexes — video stage `z-0`, play/pause `z-20`, subtitle dual-pass container `z-30`, speed/CC popovers `z-30`, controls bar `z-40`, Quick Settings `z-50`. The player root and the controls bar both carry `isolate` (self-contained stacking contexts), so the controls/OSD/subtitles always paint above the `z-0` native surface and can never be trapped or clipped by a parent stacking context change; the sidebar is `opacity-100` (provably opaque). **Click routing is part of the contract**: the base native stage carries `pointer-events-none` (the host frame never intercepts ahead of a DOM control), and the controls bar toggles `pointer-events-auto`/`pointer-events-none` exactly with its opacity — an auto-hidden (`opacity-0`) `z-40` bar used to stay click-hit and swallow every pause/resume click over the stage (the intermittent "pause doesn't work" symptom); while hidden, clicks fall through to the `z-20` play/pause capture layer that calls `togglePlay`, and moving the mouse re-enables the bar. If you add a new overlay, give it an explicit layer + pointer-events decision or captions/OSD can land under the VLC video view on macOS/Windows/X11. **The player never out-stacks the sidebar**: the sidebar is `z-40` at ALL widths (no `md:z-10` — that downgrade let the player's `relative` z-auto column fail to create a stacking context, so its `z-40`/`z-50` DOM overlays were promoted into the content row and painted ABOVE the sidebar on any spatial leak). The `data-player-viewport` column is `z-0` so the whole player subtree (including its high-z popovers) is trapped in its own stacking context, structurally below the opaque sidebar. **Inline-vs-drawer is PLATFORM-driven, not width-driven**: `sidebarLayoutMode(isMobileDevice(), innerWidth)` (`videoLayout.ts`, `MD_BREAKPOINT_PX = 768`) decides the sidebar's `position`. Desktop (macOS/Windows/Linux Tauri + desktop browsers via the `isMobileDevice()` UA/touch-points check in `tauri.ts`) is ALWAYS `relative`/inline — the sidebar pushes the video aside even in a sub-768px window, so a session-restored small frame can never turn it into a layer floating over the picture (the earlier bug: any window below `md` silently became a drawer overlay). Only real touch devices (Android/iOS) get the `absolute` drawer below `md` (`md:relative md:shadow-none` upgrades a rotated phone/tablet inline, and the App backdrop that dims the video is gated by the same `isMobileDevice()`). The reporter's boundary fallback reads the sidebar's ACTUAL computed `position`, so desktop-narrow now also counts as inline there (covered by `tauri.test.ts` "isMobileDevice…" + `videoLayout.test.ts` "desktop is always inline…").

## Command surface & app subsystems

- **Transcription/dialog/file commands** (`src-tauri/src/main.rs`): pipeline = `start_transcription` (job-scoped) / `cancel_transcription` / `poll_transcript_cues(job_id)` (drains the `RenderQueue`) / `transcription_active(job_id)`; models = `download_whisper_model` / `delete_whisper_model` / `list_downloaded_models` / `check_model_downloaded`; subtitles = `open_subtitle_dialog` / `save_subtitle_dialog` (srt/vtt/ass/ssa), `read_subtitle_file` (parses via `parse_srt`/`parse_vtt`/`parse_ass`), `write_subtitle_file` (exports srt/vtt/ass); projects = `open_project_dialog` / `save_project_dialog` / `write_project_file` / `read_project_file` (`.zan` JSON; `read_project_file` validates `PROJECT_VERSION` and returns `(data, media_exists)` so the UI can warn about a moved video without failing the subtitle restore); `open_video_dialog` (extension-classified — see the media-format bullet); `extract_audio` (internal — the bundled `ffmpeg` sidecar run via the Rust `shell()` handle, 16 kHz mono s16le WAV); `write_file` (legacy; the frontend wrapper is dead code); `relaunch_app` (`tauri::process::restart`, used by the updater after install).
- **Transcription/model events** (`main.rs`): `transcription-progress`, `transcription-done {job_id,total}`, `transcription-error`, `transcription-batch-done`, `transcript-segment` (one cue per emit, streaming), `transcript-cues-ready`, `model-download-progress {model,downloaded,total}`. All carry `job_id` (see the job-identity bullet).
- **Frontend subsystems**: Zustand `store.ts` persists everything under one key (`zanplayer-lite-storage` — theme, subtitle style, whisper model, spoken-language/output/generation mode, player volume/speed, plus Recents capped at `MAX_RECENT_FILES` (20) with crash-safe resume via `hasLoadedRecentFile`). Projects (`project.ts`) hydrate the store directly from a `.zan` file, bypassing Whisper entirely. Updater (`updater.ts` + `UpdateModal.tsx`) uses plugin-updater 2.10, checks GitHub Releases on launch (background + manual), and `installAndRestart` → backend `relaunch_app`. PWA: `public/sw.js` service worker + `manifest.json` register ONLY on production web builds (`import.meta.env.PROD && !isTauri()`); `useInstallPrompt.ts` defers the Chrome/Edge install prompt (`beforeinstallprompt`).
- **`src-tauri/capabilities/main.json`** is the Tauri 2 permission file for the `main` window: core, dialog, fs (app-scoped recursive read/write/meta), `http:default` + `updater:default`. No `shell` capability is needed — the FFmpeg sidecar and native-player/updater paths all run backend-side, never through an IPC-gated shell command.
- **Native IPC surface** (`native_player/mod.rs`): `vlc_is_available`, `native_layout_debug` (always `false` — kept so the invoke surface stays stable after the old Render-API debug border was dropped), `vlc_set_layout`, `set_window_fullscreen`, `start_window_drag`, `vlc_load` / `vlc_play` / `vlc_pause` / `vlc_seek` / `vlc_set_volume` / `vlc_set_speed` / `vlc_stop`. Events: `vlc-timeupdate` (250 ms coalesced), `vlc-loaded`, `vlc-embed-ok` (load-time embed probe), `vlc-embed-lost` (macOS per-beat host probe, once per load; also mobile poll failure), `zan-fullscreen`.

## Mobile playback backends (Android/iOS)

The mobile plugins use the exact same `vlc_*` command surface as the desktop engines — the webview never sees a difference:

- **Rust bridge** (`mobile.rs`, `mobile_android.rs`, `mobile_ios.rs`): `MobileSession` holds a `PluginHandle<Wry>` from the managed `MediaPlaybackState`. `load()` runs `CMD_LOAD`, spawns a single 250 ms ticker thread (swap-once guard) polling `CMD_POSITION` → coalesces via `snapshot_changed` → emits `vlc-timeupdate`; persistent poll failure emits `vlc-embed-lost` once and breaks (same recovery path as desktop). `apply_surface_layout` is a deliberate no-op (mobile native surfaces fill the whole window behind the transparent webview) — when the mobile sidebar is a **drawer overlay**, the opaque drawer paints OVER the video (standard mobile UX), never the reverse; the video's `data-player-viewport` column spans the full window there, and the frontend reporter dispatches it verbatim (drawer mode never shrinks the column). Shared helpers (`snapshot_changed`, `position_clamped`, `POSITION_EPSILON`) live in `mod.rs` and are used by both desktop session tickers and the mobile poller.
- **Plugin registration**: one always-present `.plugin(native_player::mobile_media_init())` slot in the Builder chain (`main.rs`). On desktop this returns an empty no-op `TauriPlugin`; on mobile it delegates to `mobile_android::init()` / `mobile_ios::init()`, each of which calls `api.register_android_plugin(…)` / `api.register_ios_plugin(…)` and stashes the handle in `MediaPlaybackState`. Registration failure is non-fatal (logged; `MobileSession::new` then errors → frontend falls back to HTML5).
- **Android** (`mobile/android/MediaPlaybackPlugin.kt`): Media3 ExoPlayer 1.11.0, `@TauriPlugin class MediaPlaybackPlugin(activity)`, `load(webView)` sets the WebView transparent. Commands: `load` (resolve URI → ExoPlayer), `play`/`pause`/`stop`, `seek` (ms→s), `set_volume` (0–100 → 0.0–1.0), `set_speed`, `position` (currentPosition ms→s / duration / isPlaying / STATE_ENDED), `diagnostics`.
- **iOS** (`mobile/apple/MediaPlaybackPlugin.swift`): AVFoundation AVPlayer + `PlayerSurfaceView` (layerClass = AVPlayerLayer) below the WKWebView. `@_cdecl("init_zanplayer_media")` bridges to the Rust `ios_plugin_binding!` macro. `load(webview:)` makes the webview transparent; same command set. `stop` does `replaceCurrentItem(nil)` to release source.
- **Command contract** (verified against `mobile.rs` and the position-response test): command verbs = `load`, `play`, `pause`, `seek`, `set_volume`, `set_speed`, `stop`, `position`, `diagnostics`. Argument keys = `path`, `position` (f64, seconds), `level` (f64, 0–100), `speed` (f64). `position` response = `{ position, duration, paused, ended }` (camelCase).
- **Plugin locations** (as of this commit, the mobile plugin source lives in `src-tauri/mobile/{android,apple}/`, NOT yet copied into `src-tauri/gen/`). After running `npx tauri android init` or `npx tauri ios init`, copy the files into the generated projects — the exact paths are documented in each platform's `README.md` under `src-tauri/mobile/`.
- **Honest verification status**: the Rust bridge compiles and is covered by unit tests (`cargo test`, `cargo clippy`, `cargo build --features vlc-native` on macOS). The **Kotlin and Swift files have never been compiled or run** — no JDK, Android SDK, Xcode, or Rust mobile targets exist on the dev machine. They are written against the documented Tauri v2 mobile plugin APIs (`app.tauri.annotation.*`, `Invoke.parseArgs`, `@_cdecl`) and Media3/AVFoundation, but will need device-time fixes.
