# Project agent notes

## Commands
- Frontend: `npm run dev`, `npm run build` (`tsc && vite build`), `npm run test` (vitest)
- Rust: `cargo test` then `cargo build --features native-player` (must keep linking)
- Native engine: `npm run tauri dev -- --features native-player` (Windows/Linux wid path); on macOS native playback requires `--features macos-render` (Render-API backend, see below)
- Release: `npm run release -- <major|minor|patch>` (the only path that builds a GitHub release; plain `git push` runs only tests)
- Smoke test: `ZANPLAYER_NATIVE_SMOKE=1 ZANPLAYER_NATIVE_SMOKE_VIDEO=/path/to.mp4 npm run tauri dev -- --features native-player` — auto-loads a file through the real mpv session and prints `[native-smoke]` layering/attach logs to stderr. On macOS use `-- --features macos-render`; the smoke then runs an **11-check battery**: (1) render context error-free, (2) ≥1 frame presented via Metal, (3) `vo=libmpv` decoding, (4) clock advancing, (5) webview DOM not occluding the layer, (6) stage re-anchoring to a single window resize, (7) **sidebar reflow (mini/extend) re-anchors the stage exactly + stays transparent**, (8) **multi-step manual resize re-anchors exactly with no drift + transparent**, (9) **native fullscreen enter/exit re-anchors + transparent**, (10) **the product's web-Fullscreen-API button path re-anchors to the full window + transparent**, (11) **a sub-`md` (640-wide) desktop window still keeps the sidebar INLINE — ON pushes the stage right of the opaque sidebar, OFF fills the row; the old width-driven drawer-over-video conflict must not return** — and prints `[native-smoke] RESULT: N/11 passed`; the `applied` rect each check compares to the DOM stage is the ACTUAL rendered host frame (`macos_surface::applied_js_rect`), so a misconverted or drift-accumulated surface fails instead of hiding behind the requested rect. Checks 7 and 11 additionally print a `[native-smoke] conflict-view` horizontal paint-profile scan (`window.__zanSmokeScan()`, one char per 16 CSS px across the whole window): `S` = topmost element lives inside the opaque `[data-sidebar]` subtree, `o` = opaque webview over the video, `.` = see-through stage, `1`..`8` = intermediate alpha — so "sidebar ON" is provably opaque-left / transparent-right at every window size and any video bleed-over-the-sidebar fails the scan, not just the rect math. Because the harness webview sits in the app's empty state (player root paints opaque `bg-black` until the frontend knows `engine === "mpv"`), the smoke injects a rAF + `resize`/`fullscreenchange` tracking loop that asks the webview for the **player-viewport rect** (the App shell's content column — the same measure the product's layout reporter feeds `mpv_set_layout`). `findArea()` walks **every descendant** of `#root > div` (not just direct children — the app root now wraps the top bar + a "content row" holding sidebar + stage) and selects the **smallest** element whose rect reaches the bottom-right corner (±1px), which excludes the top bar (bottom edge short), the sidebar (right edge short) and absolute overlays; windowed stage rects therefore carry a `y≈40` (the `h-10` chrome strip). It injects a smoke-only stylesheet clearing DOM backgrounds *inside that area* only (the sidebar keeps its paint, so the smoke reproduces the real layout: opaque chrome right, video stage right — desktop no longer bleeds through since the strip paints solid), anchors the CAMetalLayer to that rect and re-anchors it on every layout change, then has the webview report the DOM alpha over the area centre (`plugin:event|emit` → `native-smoke-layout`/`native-smoke-occlusion`/`native-smoke-measure` → Rust `app.listen`) — so the decoded picture is *actually visible during the smoke and confined to the player stage*, and a regression that buries the video under an opaque surface (or stops tracking window resizes / sidebar reflow / fullscreen) fails the checks instead of just playing sound. Each transition check asserts **applied rect == DOM stage rect (±2 px)** AND **DOM alpha < 0.5**; `settle()` waits for 2 s of *stable* applied-rects so the macOS fullscreen animation (~1.5 s) can't be misread as the final rect; resize targets are derived from the applied stage rect × window scale factor (never `inner_size()`, which a session-restored oversized frame makes a no-op). Check 10 drives `document.documentElement.requestFullscreen()` (the exact product button path, which also auto-hides the sidebar to x≈0) and is **skipped, not failed**, if the webview session doesn't implement the Fullscreen API.

## Native player engine
- In-window libmpv engine behind the `native-player` cargo feature; shipped builds are feature-off (HTML5 `<video>` is the default).
- Uses the **`libmpv2`** crate (client API 2.x; the crate links 2.2, `Mpv::new` enforces only a *major* match) so current mpv works — Homebrew 0.41 with client API 2.5 inits fine (verified: `vo=gpu-next`, `hwdec=videotoolbox`). The old `libmpv` crate pinned 1.108 and was rejected by modern mpv ("VersionMismatch").
- **`wid` must be set as a pre-init OPTION** (`Mpv::with_initializer` → `init.set_option("wid", surface)`). A post-init runtime `set_property("wid", ...)` returns OK but mpv 2.x never spawns its video view. `keep-open` and `hwdec` are set as init options too. After init, `MpvSession::new` asserts `get_property("wid")` still equals the surface (embed guard) — a mismatch means the VO ignored the embed and would open a DETACHED window (external/PIP symptom), so the session fails and the frontend falls back to HTML5. On macOS the session also runs `macos_surface::verify_embedded` (host NSView must have a superview + window + non-zero frame) or it refuses to attach.
- **macOS uses the libmpv Render API, not the window VO**: `macos-render` (implies `native-player`) swaps in `render::RenderSession` behind the same `MpvControl`/commands. `MpvSession` (the `wid` path) is still compiled on macOS only as the `macos_surface` host-view + clock provider (its window-VO code is `#![cfg_attr(allow(dead_code))]` there). The render backend: init `vo=libmpv` (never `wid` — a detached window is structurally impossible), `hwdec=no` (frames land in CPU memory; GPU decode would copy straight back), then `mpv_render_context_create` with `MPV_RENDER_API_TYPE_SW`. The host view's backing layer is replaced with a **CAMetalLayer** (BGRA8Unorm, `framebufferOnly=false`, opaque, `contentsScale=backingScaleFactor`, drawableSize = stage px) created via raw `AnyClass::get(c"CAMetalLayer")` + `MTLCreateSystemDefaultDevice` (declared locally with `#[link(name = "Metal", kind = "framework")]`). The render thread polls `mpv_render_context_update` → `mpv_render_context_render` into a 64-byte-aligned-stride `bgr0` buffer, forces the 4th byte (alpha) to 0xFF, then `replaceRegion`s into the next drawable's texture and commits a `presentDrawable` command buffer; `report_swap()` after each successful render. Metal/QuartzCore types are NOT `Send` (objc2) so all objects live behind leaked raw `ObjPtr(*mut AnyObject)` + manual `Send/Sync` (the `ViewPtr` pattern), and by-value `MTLRegion`/`MTLOrigin`/`MTLSize`/`CGSize` get `unsafe impl Encode`. `<video>`-less HTML captions/OSD sit in the webview above the layer; a poll-loop `frame_requested: AtomicBool` latch wakes the thread and also doubles as the redraw request for play/pause/seek/layout changes. `render/macos_render.rs` drives one render thread per process (`RENDER_THREAD_STARTED`) — the Render API must be used from a single thread.
- **macOS embed target is a DEDICATED host NSView, never the WKWebView/window view.** The classic "mpv opens a separate floating window" bug is WebKit pruning foreign subviews of the webview it owns. `session.rs` → `embed_surface` returns `macos_surface::host_view(app)`: a plain layer-backed (`setWantsLayer`), retina-aware (`contentsScale = backingScaleFactor`) NSView inserted as a sibling BELOW the transparent webview (`addSubview:positioned:NS_WINDOW_BELOW`), cached in a leaked `Mutex<Option<ViewPtr>>`. objc2 0.6 gotchas it encodes: raw `*mut AnyObject` statics need a `Send + Sync` wrapper (`ViewPtr`) for `MsgSend`-able access, and by-value marshalled `NSPoint/NSSize/NSRect` need `unsafe impl Encode` (`Encoding::Struct("CGPoint"/"CGSize"/"CGRect", …)`).
- **Stage anchoring = `mpv_set_layout`**: `VideoPlayer.tsx` runs a layout reporter while `engine === "mpv"` that reads the canonical `[data-player-viewport]` column's `getBoundingClientRect()` (CSS px, top-left origin) — the App shell's content column that is a flex sibling of the sidebar — and invokes `mpv_set_layout` with a `SurfaceLayout { x, y, width, height }`. It is event-driven: a viewport `ResizeObserver` plus explicit `window` `resize` + `document` `fullscreenchange` listeners coalesce into at most one rAF per frame; a `mpv-loaded` event re-asserts the anchor after a fresh host. Sidebar toggles cause App shell flex reflow, which fires the viewport's RO — the Player never subscribes to sidebar state. **The Player consumes the PlayerViewport rect VERBATIM** (regression-covered by `VideoPlayer.test.tsx` "re-anchors exactly when sidebar expand/collapse reflows the PlayerViewport") — it never re-derives the rect against sidebar geometry: App shell flex already placed the column, so the measured box IS the region. The one exception is a **right-of-sidebar INVARIANT** (`enforceRightOfSidebar` in `videoLayout.ts`, wired into the reporter): while the OPAQUE inline sidebar is on the page (`[data-sidebar]` with `position !== "absolute"`), the rect sent to `mpv_set_layout` is forced to start at the sidebar's right edge — a stale or mid-toggle viewport rect can never make the picture paint under/over the sidebar (it is an identity in every correct flex state; test `VideoPlayer.test.tsx` `[B2]` + `videoLayout.test.ts`). Drawer mode (`position: absolute`, mobile) is NOT enforced — there the opaque drawer overlays the video by design. **Graceful missing element**: if `[data-player-viewport]` is absent the reporter sends no native layout and retries per frame until it mounts. `overflow-clip` on the `data-player-viewport` column and the player root/stage physically prevents the HTML5 fallback box and DOM overlays from painting outside the viewport — subtitles, controls, OSD are clipped; the sidebar never clips (covered by `VideoPlayer.test.tsx` "anchors the native surface to the PlayerViewport rect verbatim…"). The same module exports `playerAreaFromViewport`, the **intended** player area per platform mode (`inline sidebar open/closed`, mobile `drawer`, fullscreen) — the canonical calculation, unit-tested in `videoLayout.test.ts`. `overflow-clip` on the `data-player-viewport` column and the player root/stage physically prevents the HTML5 fallback box from painting outside the column. Values are coalesced to whole CSS px so IPC never spams. The smoke's `applied` rect is the **actual rendered host frame** read back via `macos_surface::applied_js_rect` (converted back to JS coords), never just the rect the webview requested — so a mis-anchored `setFrame:` (e.g. accumulated `convertRect` drift) fails the checks instead of hiding behind the request. Rust dispatch (`apply_surface_layout`): **macOS** `macos_surface::apply_layout` computes the host frame DIRECTLY in content coords — never `convertRect:fromView:` (its result depends on the destination view's *current* frame, so one wrong frame made every later frame drift off the stage = the "detached/misaligned surface" bug). Since the host NSView and the WKWebView are unflipped **siblings** under the content view: `content.x = webview.frame.x + x`, `content.y = webview.frame.y + webview.bounds.height − (y + h)` (flip), clamped into the webview bounds; then `setFrame:` + `setNeedsDisplay:` + `setNeedsLayout:`. The CAMetalLayer is **layer-hosting** (attached via `setLayer:`), so AppKit does NOT auto-size it — `apply_surface_layout` re-pins the layer frame to the host bounds (`masksToBounds=YES`) on EVERY `mpv_set_layout`, resizes the drawable to the stage px, and flushes CATransaction so the move lands this tick. Degenerate (0×0) rects are skipped on the Rust and JS sides so the surface can never collapse to a top-left patch while the layout settles. **Windows** `resize_mpv_video_window` scales px by `GetDpiForWindow/96` and `SetWindowPos(HWND_TOP, SWP_NOZORDER|SWP_NOACTIVATE)` on the mpv-class child (needs windows-sys `Win32_UI_HiDpi` feature); **X11** `resize_mpv_window` targets the top-most non-webview (cached) child and `configure_window` x/y/Some(width)/Some(height), DPI-scaled from root physical geometry ((px/mm)*25.4/96); **Wayland** remains a no-op. Every rect passes through `sanitize_surface_layout` (finite, non-negative).
- **Embed-loss fallback**: the ticker watches `wid` on every beat — if mpv stops resolving our surface, `session.rs` emits `mpv-embed-lost` once and stops the clock; `VideoPlayer.tsx` listens and drops straight to HTML5 (blob URL) so a detached/rogue window is never presented as in-app playback.
- **Native decode watchdog** (undecodable/corrupt files): mpv's `loadfile` returns OK for a file it ultimately cannot demux/decode (renamed path, corrupt container, headless codec), so no `mpv-load` error surfaces and the player would strand on a silent black frame. `VideoPlayer.tsx` runs a 5 s (`NATIVE_DECODE_WATCHDOG_MS`) grace timer whenever the engine is `mpv`: if the 250 ms clock never reports a real duration or advancing playhead (`nativeDecodeProvenRef`, set by the clock-mirror listener), it cuts back to the HTML5 blob engine exactly like an embed loss — the fallback's own `onError`/container hint then explains the failure. It must NOT register a competing `mpv-timeupdate` listener (the test harness stores one listener per event name, which would clobber the clock mirror) — it reads the shared decode-proof ref instead.
- macOS transparency requires BOTH `app.macOSPrivateApi: true` (tauri.conf.json) AND the `macos-private-api` tauri feature (Cargo.toml). Without them the webview stays opaque and the mpv surface is invisible.
- **App-window frame integrity / no background bleed**: the window is `transparent: true` so the Metal surface (behind the webview) shows through — chrome must paint its own opaque DOM backgrounds. `tauri.conf.json` uses `"titleBarStyle": "Overlay"` + `"hiddenTitle": true` (Tauri 2.11.2 schema `WindowConfig`) so the native macOS title bar is gone and the traffic lights float over the DOM; `App.tsx` renders a solid `h-10` top strip with `data-tauri-drag-region` (theme `bg-zan-black`/`bg-white` + border-b) holding the `Open sidebar` hamburger, and the content row (`relative flex min-h-0 flex-1 overflow-hidden`) wraps `Sidebar` + the main column. On macOS the strip clears the traffic-light group with `pl-[76px]` (gated by the `isMacOs()` UA check in `tauri.ts`; non-Mac keeps `pl-2`), so the `Open sidebar` toggle never crowds the native close/minimize/zoom buttons; the `flex-1` drag region fills the rest with `pr-2`. Desktop can no longer show through the title bar because the strip itself is opaque; the main area is covered by the `VideoPlayer` root (`bg-black` in every non-native state). The top strip is hidden in web fullscreen via `isFullscreenUi` (a `fullscreenchange` listener mirrors `document.fullscreenElement`). Do NOT set `data-tauri-drag-region` on interactive children — React renders the literal string `"false"` for data-* attributes; leaves them attribute-free (buttons inside a drag-region strip still receive clicks, matching Tauri's default titlebar template).
- mpv `wid` embed adds its video view ABOVE the webview, burying HTML captions/OSD. `src-tauri/src/native_player/session.rs` → `keep_webview_on_top` re-runs on each ticker beat and after every `load`, dispatching per-platform: **macOS** `macos_layering` re-sorts NSWindow subviews each tick so the transparent webview (DOM chrome) is topmost; **Windows** `windows_layering` finds the child HWND whose class is `"mpv"` and `SetWindowPos`s it to HWND_BOTTOM; **X11** `x11_layering` caches the webview XID from the pre-mpv child set and re-raises it (ConfigureWindow/StackMode::Above) above mpv's stacked-on-top child. **Wayland has no client-side z-order** — stacking is compositor-owned, so the frosted captions may sit under the video there (no back-end by design).
- The Windows (`windows_layering`) and X11 (`x11_layering`) FFI modules are `cfg`-gated and do NOT compile on the macOS host. They are type-checked against real `windows-sys` / `x11rb` versions via throwaway scratch crates in the system temp dir (the full cross `cargo check` is blocked by the `ring` C toolchain). If you touch those arms, re-verify that way — `cargo test`/`clippy` on macOS will not see them.
- **PTS sync**: `mpv-timeupdate` is a ~250 ms ticker that is now **coalesced** — `session.rs` emits only when `snapshot_changed` (position moved ≥ `POSITION_EPSILON` (0.05 s) vs the last beat, or paused/ended/duration changed). The React clock, progress bar, and subtitle render queue read strictly from this single payload (`mpvClock`), never from HTML5 `timeupdate`/rAF, so there is one source of truth for time.
- **Unified native seek funnel**: `VideoPlayer.tsx` `seekNative` (via `seekNativeRef`) is the ONLY native-mode seek path — drag bar, skip fwd/back, seek-to editor clicks, and auto-resume all route through it. Contract: `clearPendingSeek()` → clamp target to known duration → optimistic `setCurrentTime` (drives editor/recents; the playback clock stays on the backend tick) → `notifyPipelineSeekRef.current(target)` → `mpvSeek`. Backend: `seek_transcription` purges the `RenderQueue` (stale pre-seek cues) BEFORE forwarding through `SeekControl`/`seek_rx`, so live passes drop their VAD buffers and reposition the WAV reader to the same PTS.
- **Job identity / render-queue scoping**: every `start_transcription(..., jobId)` run is scoped by `job_id` back-to-front. The queue stores `QueuedCue { job_id, cue }` and is drained per-job (`poll_transcript_cues(job_id)` → `drain_job`), purged per-job on seek (`clear_job`), and all `transcription-progress`/`done`/`error`/`batch-done` events carry `job_id`. A new managed `ActiveJob { job_id }` slot is set at start, compare-and-cleared at job end, and read by `transcription_active(job_id)` — the frontend polls it every 150 ms as a completion safety net so a *missed* final event (fast batch run, listener torn down mid-job) never strands the `isTranscribing` flag and silently blocks the next auto-transcription. Frontend guards drop any event whose `job_id` doesn't match `transcriptionJobIdRef.current` (a previous file's still-decoding job can't surface cues or finalize state). Language change regenerates the generated track exactly once per spoken ISO code (`lastGenLanguageRef`), so stale generated tracks from the old language never linger. A failed run surfaces a **Retry** action in the CC menu that clears the error, drops partial generated tracks (`removeGeneratedTracks`), and starts a fresh job for the same file (`retryTranscription`) — no video reload, and the fresh `job_id` isolates it from the dead worker.
- **HTML5 fallback container limits**: WebKit/Safari can't demux MKV/AVI/FLV/WMV and Chromium plays a narrow MKV codec subset, while native mpv handles every catalogued container. `mediaFormats.ts` ships `isHtml5Playable(fileName)` / `html5UnsupportedHint(fileName)`; the `<video onError>` overlay (`videoLoadError`, `z-[25]`) shows a visible "this container isn't supported by the fallback player" message instead of a silent black frame — subtitles can still appear since ffmpeg decodes the audio natively. **Every media entry point classifies by file extension only** (`isMediaFile(file.name)`, lowercased): App root drag-drop, Sidebar browser `<input>`, Sidebar drag-drop, and the native `open_video_dialog` filter — browser/OS MIME types are never consulted, so an MKV drop labeled `audio/*` (or empty) can't be misrouted as audio.
- **Z-order layer scale** (native): root stays transparent; DOM overlay stack must keep explicit Tailwind z-indexes — video stage `z-0`, play/pause `z-20`, subtitle dual-pass container `z-30`, speed/CC popovers `z-30`, controls bar `z-40`, Quick Settings `z-50`. If you add a new overlay, give it an explicit layer or captions/OSD can land under the mpv video view on macOS/Windows/X11. **The player never out-stacks the sidebar**: the sidebar is `z-40` at ALL widths (no `md:z-10` — that downgrade let the player's `relative` z-auto column fail to create a stacking context, so its z-40/z-50 DOM overlays were promoted into the content row and painted ABOVE the sidebar on any spatial leak). The `data-player-viewport` column is `z-0` so the whole player subtree (including its high-z popovers) is trapped in its own stacking context, structurally below the opaque sidebar. **Inline-vs-drawer is PLATFORM-driven, not width-driven**: `sidebarLayoutMode(isMobileDevice(), innerWidth)` (`videoLayout.ts`, `MD_BREAKPOINT_PX = 768`) decides the sidebar's `position`. Desktop (macOS/Windows/Linux Tauri + desktop browsers via the `isMobileDevice()` UA/touch-points check in `tauri.ts`) is ALWAYS `relative`/inline — the sidebar pushes the video aside even in a sub-768px window, so a session-restored small frame can never turn it into a layer floating over the picture (the earlier bug: any window below `md` silently became a drawer overlay). Only real touch devices (Android/iOS) get the `absolute` drawer below `md` (`md:relative md:shadow-none` upgrades a rotated phone/tablet inline, and the App backdrop that dims the video is gated by the same `isMobileDevice()`). The reporter's boundary fallback reads the sidebar's ACTUAL computed `position`, so desktop-narrow now also counts as inline there (covered by `tauri.test.ts` "isMobileDevice…" + `videoLayout.test.ts` "desktop is always inline…").

## Mobile playback backends (Android/iOS)

The mobile plugins use the exact same `mpv_*` command surface as the desktop engines — the webview never sees a difference:

- **Rust bridge** (`mobile.rs`, `mobile_android.rs`, `mobile_ios.rs`): `MobileSession` holds a `PluginHandle<Wry>` from the managed `MediaPlaybackState`. `load()` runs `CMD_LOAD`, spawns a single 250 ms ticker thread (swap-once guard) polling `CMD_POSITION` → coalesces via `snapshot_changed` → emits `mpv-timeupdate`; persistent poll failure emits `mpv-embed-lost` once and breaks (same recovery path as desktop). `apply_surface_layout` is a deliberate no-op (mobile native surfaces fill the whole window behind the transparent webview) — when the mobile sidebar is a **drawer overlay**, the opaque drawer paints OVER the video (standard mobile UX), never the reverse; the video's `data-player-viewport` column spans the full window there, and the frontend reporter dispatches it verbatim (drawer mode never shrinks the column). Shared helpers (`snapshot_changed`, `position_clamped`, `POSITION_EPSILON`) live in `mod.rs` and are used by both desktop session tickers and the mobile poller.
- **Plugin registration**: one always-present `.plugin(native_player::mobile_media_init())` slot in the Builder chain (`main.rs`). On desktop this returns an empty no-op `TauriPlugin`; on mobile it delegates to `mobile_android::init()` / `mobile_ios::init()`, each of which calls `api.register_android_plugin(…)` / `api.register_ios_plugin(…)` and stashes the handle in `MediaPlaybackState`. Registration failure is non-fatal (logged; `MobileSession::new` then errors → frontend falls back to HTML5).
- **Android** (`mobile/android/MediaPlaybackPlugin.kt`): Media3 ExoPlayer 1.11.0, `@TauriPlugin class MediaPlaybackPlugin(activity)`, `load(webView)` sets the WebView transparent. Commands: `load` (resolve URI → ExoPlayer), `play`/`pause`/`stop`, `seek` (ms→s), `set_volume` (0–100 → 0.0–1.0), `set_speed`, `position` (currentPosition ms→s / duration / isPlaying / STATE_ENDED), `diagnostics`.
- **iOS** (`mobile/apple/MediaPlaybackPlugin.swift`): AVFoundation AVPlayer + `PlayerSurfaceView` (layerClass = AVPlayerLayer) below the WKWebView. `@_cdecl("init_zanplayer_media")` bridges to the Rust `ios_plugin_binding!` macro. `load(webview:)` makes the webview transparent; same command set. `stop` does `replaceCurrentItem(nil)` to release source.
- **Command contract** (verified against `mobile.rs` line 34–42 and the position-response test): command verbs = `load`, `play`, `pause`, `seek`, `set_volume`, `set_speed`, `stop`, `position`, `diagnostics`. Argument keys = `path`, `position` (f64, seconds), `level` (f64, 0–100), `speed` (f64). `position` response = `{ position, duration, paused, ended }` (camelCase).
- **Plugin locations** (as of this commit, the mobile plugin source lives in `src-tauri/mobile/{android,apple}/`, NOT yet copied into `src-tauri/gen/`). After running `npx tauri android init` or `npx tauri ios init`, copy the files into the generated projects — the exact paths are documented in each platform's `README.md` under `src-tauri/mobile/`.
- **Honest verification status**: the Rust bridge compiles and is covered by unit tests (`cargo test`, `cargo clippy`, `cargo build --features native-player,macos-render` on macOS). The **Kotlin and Swift files have never been compiled or run** — no JDK, Android SDK, Xcode, or Rust mobile targets exist on the dev machine. They are written against the documented Tauri v2 mobile plugin APIs (`app.tauri.annotation.*`, `Invoke.parseArgs`, `@_cdecl`) and Media3/AVFoundation, but will need device-time fixes.
